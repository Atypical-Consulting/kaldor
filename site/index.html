How Kaldor works

No commit made by Claude Code enters your repository without being checked against an intent you approved, by a reviewer the agent does not control.

1The intent comes first

Before its first edit, Claude writes .kaldor/intent.md: goal, expected behavior, what must not be touched, expected files. You approve it, kaldor intent freeze records its hash, and you confirm it from your terminal with kaldor intent confirm.

2Claude commits as usual

A plain git commit from the Bash or PowerShell tool. Nothing changes in how Claude works.

3The hook stops the call

Claude Code runs Kaldor's PreToolUse hook before every Bash and edit call. It fails closed: a hook that crashes, times out or gets no verdict from the reviewer blocks. The same hook refuses edits until an intent is frozen.

4The gate checks the hashes

kaldor gate finds the commit in the command line, even through git -C, cd, bash -c or an alias, and refuses hook-skipping flags at once. It checks that the intent still matches its frozen hash, hashes the staged diff, and reuses an earlier verdict for the same diff and intent. A new diff is reviewed only once you have confirmed the intent.

5Someone else reviews

The gate launches a headless claude -p with a fixed prompt, no tools and no CLAUDE.md, and hands it the intent, the rules and the diff. The agent never writes a word of that prompt.

6The gate records the verdict

Accepted: a pass is stored in .git/kaldor/state.json for that exact diff and intent, and the command runs. Refused: exit 2, and Claude receives the deviations to fix. Every review is logged in .git/kaldor/log/.

7A second lock at git

The git pre-commit hook runs kaldor check, the same evaluation, on the index git is about to commit. When the gate already passed that diff, it costs nothing. When it did not (a commit from a script, or files staged in the same command, as in git add -A && git commit), it calls the reviewer itself, and a refusal aborts the commit. Only commits made inside Claude Code are checked; yours are not.

Plan mode or Kaldor?

Both start the same way: Claude says what it will do before touching the code, and you agree. After that, they have little in common.

Plan mode is a conversation phase. It asks Claude to think and propose a plan before editing. Once you accept it, nothing binding remains: the plan is not recorded anywhere in a form that can be checked, nobody checks the code against it, Claude can drift from it, widen the scope or touch files nobody expected, and it lives only in that session. Another session or another worktree knows nothing of it.

A Kaldor intent is a contract checked at every commit.

  • Frozen by hash. Editing intent.md mid-task is refused; a change goes through an amendment only you can accept.
  • Confirmed by you, outside the session. kaldor intent confirm needs an interactive terminal, so Claude cannot vouch for its own intent.
  • Checked by an independent reviewer. At every commit, a separate claude -p reads only the intent, the rules and the staged diff, never the conversation. It refuses scope creep, changes to sensitive paths, weakened tests and anything that contradicts the intent.
  • Enforced by hooks, not by Claude's goodwill. The PreToolUse hook and the git pre-commit hook block, and the usual shortcuts are closed: --no-verify, writing Kaldor's state, an approve run by Claude.
  • Traced. Every freeze, confirmation, review and forced approval is logged, and kaldor report shows them across worktrees.
Plan modeKaldor intent
RoleHelps think before actingA contract enforced up to the commit
WhenBefore editing, then forgottenThe whole task, checked at every commit
Who guarantees itClaude itselfAn independent reviewer and hooks
TraceNoneA log you can read

The two work together. Use plan mode to explore and shape the solution, then draw the Kaldor intent from it (goal, expected behavior, what must not be touched, expected files): that intent becomes the reference every commit is judged against.

BInstall

You need the .NET 10 SDK (for dnx), Claude Code 2.1.295 or later, and git. The .NET tool is never installed: the hooks run it through dnx, which fetches the version the plugin pins on first use.

  1. Once per machine, in Claude Code, install the plugin. It brings the hooks, the intent skill and a kaldor command for the agent.

    /plugin install kaldor --marketplace Atypical-Consulting/kaldor

  2. Once per repository, from your terminal, enable Kaldor. This creates .kaldor/rules.json and the git pre-commit hook (if one already exists, it prints the line to add to it). Kaldor stays silent in repositories without .kaldor/rules.json.

    dnx Atypical.Kaldor init

  3. Commit the rules yourself, from a regular terminal, not through Claude. Kaldor refuses Claude's commits until a task intent is frozen and confirmed, so enabling Kaldor, like any later change to the rules, stays your decision.

    git add .kaldor
git commit -m "chore: enable Kaldor"

  4. Check the installation at any time.

    dnx Atypical.Kaldor doctor

Prefer typing kaldor? dotnet tool install -g Atypical.Kaldor. The rest of this page uses that short form.

CDay to day

Work with Claude Code as usual. Kaldor steps in twice per task.

  1. Start from a clean work tree. Claude writes the intent and shows it to you. Edits are refused until it is frozen.

    # Intent
Goal: add pagination to the GET /orders endpoint
Expected behavior: page and size parameters, 50 by default
Must not touch: the database schema, authentication
Expected files: OrdersController.cs, OrdersQuery.cs, related tests

  2. Approve or correct it. Claude then runs kaldor intent freeze.

  3. Confirm it from a terminal outside Claude Code, any time before Claude's first commit: dnx Atypical.Kaldor intent confirm, or kaldor intent confirm with the global tool. The ! prefix in Claude Code has no terminal, and the confirmation needs one. Claude can freeze an intent, but only you can vouch for it, so commits wait for you.

  4. Each commit is reviewed, in a few seconds. An accepted commit goes through; a refused one comes back to Claude.

  5. Read the report when you want: intents, deviations, and the hunks worth your attention.

    $ kaldor report
2026-10-17 23:30  review          BLOCKED
  deviation  README.md: modified despite the intent saying it must not be touched.
  deviation  greet.py: adds a network call to http://example.com/track that sends the user's name.
  to read    greet.py (logic)
  summary    The diff adds an undeclared tracking request in greet.py and edits README.md, which the intent forbids.

When a commit is refused

The deviations go back to Claude, which fixes the code and commits again. The same diff against the same intent gets the same answer without a second review. A diff staged in the same command as the commit is refused one step later, by the pre-commit hook, which aborts the commit.

When the intent itself must change

Mid-task, the intent cannot be edited or frozen again. Claude proposes an amendment, and only you can accept it:

kaldor intent amend "Also add an index on orders.created_at."   # Claude
kaldor intent amend --accept                                     # you, in your terminal

When you disagree with the reviewer

Force the exact staged diff through with kaldor approve, from a terminal outside Claude Code (dnx Atypical.Kaldor approve without the global tool). intent confirm, approve and amend --accept are all refused to the agent twice over: the gate denies the command, and the command itself needs an interactive terminal.

DCommands

ERules

.kaldor/rules.json is versioned with the repository. Comments and trailing commas are accepted.

{
  "sensitive": ["**/Auth/**", "**/Migrations/**", "**/appsettings*.json", ".github/**"],
  "trivial": ["**/*.md"],
  "reviewer_model": "sonnet",
  "block_on": ["scope_creep", "sensitive_change", "weakened_tests", "contradicts_intent"]
}
KeyMeaning
sensitivePaths whose changes the intent must announce. The reviewer is asked to flag them as must-read in the report.
trivialPaths the reviewer may summarise as mechanical.
reviewer_modelThe model the reviewer runs on.
confirm"before" (default): commits wait for kaldor intent confirm. "after", for unattended sessions: unconfirmed commits still go to the reviewer and are logged as unconfirmed; kaldor report --unconfirmed lists them. Only you can set it.
trivial_max_linesOptional, off by default. A confirmed task may commit up to this many changed lines in total, outside sensitive paths and without binary or mode changes, with no model review (logged as trivial). The budget belongs to the intent, so splitting a change does not escape review. A one-line Goal: ... intent is enough for a small fix.
block_onThe deviation categories the reviewer is told to block on: scope_creep, sensitive_change, weakened_tests, contradicts_intent.

.kaldor/intent.md is local and ignored by git. state.json and the log/ history live in the git directory, .git/kaldor/, with one folder per linked worktree: git clean and git worktree remove leave them alone, and kaldor report shows every worktree. Claude's edit tools and the shell writes the gate recognises are refused on all of it, except on intent.md at the start of a task.

FWhat it guards against

The target is a hurried agent taking a shortcut, not a hostile one. On a local machine nothing is tamper-proof; the goal is for the honest path to be the shortest. Most shortcuts below are covered by a test in the repository.

ShortcutWhy it fails
Framing the reviewerThe hook launches the reviewer with a fixed prompt; the agent never writes a word of it.
Writing its own verdictThe verdict is produced inside Kaldor's process. Claude's edit tools, and shell writes such as redirections, cp, rm or sed -i, are refused on .git/kaldor/ and on the rules.
Rewriting the intentIt is frozen by hash; a change goes through an amendment only you can accept.
Changing code after reviewVerdicts are bound to the hash of the staged diff.
git -C, cd x &&, bash -c, aliasesThe gate parses the command line itself.
Committing from a scriptThe git pre-commit hook runs the same check for any commit made inside Claude Code.
--no-verify, core.hooksPathRefused.
Breaking the hookonFailure: "block": a failing or timed-out hook blocks.
Freezing an intent you never sawCommits wait until you run kaldor intent confirm.
Approving itselfintent confirm, approve and amend --accept are refused by the gate and need an interactive terminal.

GCosts and limits

Early measurements, on small diffs, with Sonnet as the reviewer:

MeasureEarly figure
Starting the tool through dnx≈ 0.5 s added to every Bash or edit tool call
One review4–5 s per new staged diff

The reviewer model is called once per distinct diff and intent pair; a diff already reviewed costs nothing.

Known limits

  • An agent that stashes its work gets a clean tree back and can freeze a new intent, but its commits then wait for your kaldor intent confirm.
  • A write from inside a script or an interpreter (python -c) can still reach .git/kaldor/state.json and forge a pass: the gate only sees the command line. Kaldor targets shortcuts, not tampering.
  • A staged diff over 600,000 characters is refused outright: split the commit.
  • When the reviewer fails or returns no verdict, the commit is blocked and the next attempt reviews again.
  • Narrowing the hook to save the 0.5 s would reopen the bypasses it exists to close.
